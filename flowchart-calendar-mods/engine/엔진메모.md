## 1. 이벤트 실행 통로

### 1.1 이름으로 부른다 [확인]

`LSys3xScript::RunEvent()` 하나가 모든 이벤트의 실행 지점이다.

```
전역 #214 LSys3xScript::m_FuncName       ← 실행할 이벤트 이름
전역 #190 g_EvResult                      ← 다음 이벤트 번호(0이면 끝)
전역 #213(m_IsSysScenario)                ← 이름에 접두어를 붙일지
```

`RunEvent` 의 흐름(`engine/jam/LSys3xScript__RunEvent.jam`):

1. `g_EvResult = 0`
2. `m_IsSysScenario` 가 참이면 `m_FuncName` 을 **그대로**, 거짓이면 `"ＥＶ／元／" + _AdjustOriginalName(m_FuncName)` 로 `DG_STR_TO_METHOD DG_Event` 델리게이트를 만들어 부른다.
3. 돌아와서 `■デバッグ／シナリオジャンプ無視確認()` 이 참이면 `g_EvResult = 0`.
4. `g_EvResult != 0` 이면 `m_FuncName = GetLabelName(g_EvResult)` 로 바꾸고 `■ＥＶ登録(…, INT_MIN)` 한 뒤 2번으로 돌아간다 — **이벤트 → 이벤트 사슬**.

이름 만들기 [확인]:
- `GetLabelName(no)` = `no == 1706` 이면 `"E1706"`(`E%04d`), 아니면 `E%05d`.
- `_AdjustOriginalName`: `E01707 → 01707`, `E02132 → 02132` (함수 이름이 그렇게 되어 있다).
- 그래서 이벤트 함수 이름은 `ＥＶ／元／E%05d` 가 1,161개, 여기에 `E1706` · `01707` · `02132` · `イベント初期化` 를 더해 1,165개.

### 1.2 들어오는 문 [확인]

`LSys3xScript::Prepare/PrepareSys` 를 거쳐 `RunEvent` 를 부르는 자리는 이것뿐이다.

| 부르는 곳 | 방식 | 개수 |
|---|---|---|
| `L_EventCall::Call(번호)` | `GetLabelName` → Prepare → RunEvent | 본편 스케줄러 전용 |
| `L_EventCall::CallAlways(이름)` / `CallOnce(이름)` | 이름 그대로 | 특별한 날·최종장 던전 |
| `L_RandomScenario::CallAfterTraining` / `CallWalkDungeon` | 풀에서 뽑은 번호 | 특훈 뒤·던전 걷기 |
| `C_EventDungeon****@RunEvent*` (32개 클래스) | `Prepare("Exxxxx")` 상수 | 던전 안 238자리 |
| `C_SceneModeScene@ExecScene` | 회상 표의 playEvNo | 회상 화면 |
| `C_TestScenario@ExecScenario` | `PrepareSys(전체이름)` | **개발 실행기(릴리스에서 닿지 않음, 3절)** |
| `呼出／オープニング` | `Prepare("E00001"/"E00002")` | 시작 |

`L_EventCall::Call` 을 부르는 함수는 `L_EventCall` 자기 자신뿐이다(13곳). 즉 **본편 이벤트의 날짜 판정은 전부 `L_EventCall` 안에 있다.**

### 1.3 이벤트 함수 자체는 납작하다 [확인]

1,165개 이벤트 함수의 opcode 분포: `CALLFUNC` 188,144 · `MSG` 100,830 · `PUSH` 74,433 · `S_PUSH` 31,790 · `.GLOBALASSIGN` 1,195 · `RETURN`/`ENDFUNC` 각 1,165 · `JUMP` 62 · 그 밖 소수.

- 이벤트 함수가 대입하는 전역은 **`g_EvResult` 하나뿐**(1,195회). 다른 전역은 0회.
- 분기(`IFZ`/`IFNZ`)가 있는 함수는 **21개**. EX `シナリオテストデータ` 의 `選択肢あり=1` 21행과 **완전히 같다**.
- 그 21개 어디에도 **분기 뒤 대사가 없다**(전부 0줄). 선택지는 대사를 고르지 않고 **다음 이벤트 번호만** 고른다.
  → 갈래 변형은 함수 안이 아니라 다음 함수로 갈린다. 추출 텍스트에 여러 갈래가 섞이는 문제([[vn-summary-must-respect-branch-variants]])가 이 게임에는 없다.
- 이벤트 함수가 쓰는 도우미는 **44종**뿐이고, 구조에 관계된 것은 다음뿐이다:
  `■ＡＤＶ制御`(1,090회) · `OCmd_SET_EVENT_MODE` · `■選択メッセージ／選択肢追加`(52) · `■選択メッセージ／実行`(21) · `■親密度上昇X{1,2}`(25) · `■イベント戦闘実行`(1) · `VOICE`(8,003, 133개 이벤트).
  설계도가 예상한 `■ＥＶ登録`·`■汎用フラグ`·`■閲覧／…` 직접 호출은 이벤트 함수에 **없다**.

## 2. 「읽었다」는 어디에 남나

### 2.1 Once — 이번 판 [확인]

```
LEventFlag::GetOnce(이름)  →  ■ＥＶ登録確認("ＥＶ／元／"+이름)
                            →  N_ScenarioRegister::IsRegisteredEvent
                            →  전역 array<string> N_ScenarioRegister::detail::_EV_TABLE 안에 있나
```
- 등록은 `■ＥＶ登録(이름, INT_MIN)` → `RegisterEvent`. 이름이 빈 문자열이면 `system GetFuncStackName(3)` 으로 **부른 쪽의 부른 쪽**, 곧 이벤트 함수 이름을 쓴다.
- 그래서 **이벤트가 `■ＡＤＶ制御` 를 부르는 순간 자기 이름이 등록된다**(1,087개 이벤트가 부른다).
- 사슬로 이어지는 다음 이벤트는 `RunEvent` 가 실행 **직전**에 따로 등록한다.
- `LEventFlag::GetCountOnce()` = `_EV_TABLE` 의 길이.
- 전역 배열이므로 슬롯 세이브에 통째로 들어간다 [가설 — 세이브 포맷을 열지 않았다].

### 2.2 Total — 판을 넘어 [확인, 단서 포함]

```
LEventFlag::GetTotal(이름) → ■閲覧／シナリオ登録確認(이름)
                            → N_ModeScene::GetMemModeNoFromScenario(이름)   ← 회상 번호
                            → sceneNo > 0 이면 Ａ＿回想確認 → HLL PassRegister ExistNumber(그룹 1)
                            → sceneNo <= 0 이면 **언제나 0**
```
- **중요**: `GetTotal` 은 회상 표(`EX 回想`, 76칸)에 있는 이벤트에만 값이 있다. 나머지 1,088개는 언제나 0.
- `LEventFlag::SaveTotal` / `LoadTotal` 은 본문이 `return 1` 뿐인 **빈 함수**다.
  → 설계도 D4(「seen_total 로 차트 잠금을 푼다」)를 그대로 쓰면 76칸 말고는 영원히 잠긴다. 보고서에 D4' 로 바꿔 적는다.

### 2.3 시스템 플래그 [확인]

`SystemFlagManager` = 전역 `g_sysFlagList`(int 101칸).
`Save/Load` 는 HLL `system GroupSave/GroupLoad("SaveGroup_SystemFlag", "CommonGameData.asd", "seEfa0ea?d8sdvaAekfe")`.
→ 세이브 폴더의 **252바이트짜리 `CommonGameData.asd` 의 정체가 이것**이다. `Set` 은 값이 바뀌면 곧바로 저장한다.

### 2.4 범용 플래그 [확인]

`■汎用フラグ／設定|取得(type, val)` = `Flags` 구조체의 배열칸 52(int×100). 범위 밖이면 무시.

## 3. 개발사 테스트 실행기 — 설계도 2.8 의 네 질문

### (a) 릴리스에서 닿나 — **닿지 않는다** [확인]

```
game_main:
    ...
    if (HLL system IsDebugMode) { while(1) TestStartMenu(); }   ← 디버그일 때만
    new C_GameMain; pGameMain->Run(1);                          ← 아니면 바로 본편
```
- 테스트 메뉴로 들어가는 문은 `game_main` 의 이 한 자리뿐이다(`TestStartMenu` 의 호출자 1개).
- 게다가 `Ａ＿テスト選択` 는 `if (!IsDebugMode) { while(true) AFL_View_Update(); }` — 디버그가 아니면 **영원히 멈춘다**. `C_TestScenario` 의 모든 화면이 이 함수를 쓴다.
- `C_SceneGame@RunTest` 도 첫 줄이 같은 게이트다.
- `■デバッグ／シナリオジャンプ無視確認` 도 `IsDebugMode` 가 거짓이면 언제나 거짓 → **릴리스에서는 사슬 이동을 끌 수 없다**.
- `IsDebugMode` 는 스크립트 밖(엔진 HLL)이라 여기서 값을 확인할 수 없다 [가설: 릴리스에서 거짓]. 다만 참이면 `game_main` 이 본편에 들어가지 못하므로 거짓일 수밖에 없다는 간접 근거가 있다.

→ **설계도 7.2 의 1안(원작 실행기 노출)은 스크립트만으로는 안 된다.** 2안(KR_ 이동 함수)이 길이다.

### (b) 실행할 때 문맥을 어떻게 세팅하나 — **거의 안 한다** [확인]

`C_TestScenario@ExecScenario(evName)` 의 본문은 세 줄이다.

```
system Output(…)                     ← 로그
LSys3xScript::PrepareSys(evName)     ← m_IsSysScenario = 1, m_FuncName = evName
LSys3xScript::RunEvent()
■ＡＤＶ消し(1, 0)
```

- 날짜·파티·친밀도·플래그를 **맞춰 주지 않는다**. `C_TestScenario@Run` 이 따로 해 주는 것은 두 가지뿐: 주인공 이름 치환(`Ａ＿メッセージ置換設定`)과 `L_Calendar::SetDate(월, 1, 0)`(달만 바꾸는 메뉴).
- 곧 **「그 장면을 그 문맥에서 볼 수 있게」 해 주지 않는다**. 배경·인물 그림은 이벤트 함수가 자기 안에서 다 준비하므로(`■準備背景`·`■準備立ち絵` 등) 장면 자체는 뜬다.

### (c) 부작용 [확인]

- 이벤트가 `■ＡＤＶ制御` 를 부르면 **읽음 등록과 회상 등록이 그대로 일어난다**(테스트 실행기든 본편이든 같은 경로).
- `g_EvResult` 사슬도 그대로 돈다(릴리스에서는 끌 수 없다, 위 (a)).
- 친밀도 상승 도우미가 든 25개 이벤트는 **친밀도도 오른다**.
→ 검수용 이동은 세이브를 더럽힌다. 별도 슬롯을 쓰라고 안내해야 한다(설계도 7.1).

### (d) 끝나면 어디로 — [확인]

`ExecScenario` 는 그냥 돌아온다(`■ＡＤＶ消し`). 부르는 쪽(`C_TestScenario@Run`)이 메뉴 루프로 돌아간다. `Run` 은 `res<=0 || res==99` 면 `Ａ＿タイトルに戻る＿確認なし()` 로 타이틀에 돌아간다.

## 4. 본편 스케줄러 `L_EventCall::Check` [확인]

`Check(ref int pnResult, int nTimeID, bool bLoadData, bool bLoadRestData)`.
호출자 8개: `呼出／１日の始まり`·`月曜実行`·`火〜金曜実行`·`土曜実行`·`日曜実行`·`エンディング実行`·`残時間終わり処理／日曜`·`C_SceneTraining@Run`.

맨 앞에서 전역 세 개를 오늘 값으로 채운다:
`m_nMonth = Flags.Date.月`, `m_nDay = Flags.Date.日`, `m_nTimeID = nTimeID`, `m_bUnconditionalCalled = 0`.

### 4.1 규칙 두 가지

```
UnconditionalCall(월, 일, timeID, 번호)
    오늘과 정확히 같으면  m_bUnconditionalCalled = 1;  Call(번호)
    (Call 안에서 이미 읽은 이벤트인지는 보지 않는다 — Call 은 무조건 실행)

ConditionalCall(시작월, 시작일, 끝월, 끝일, timeID, 인물, 친밀도, 선행이벤트, 번호)
    timeID 가 다르면 거짓
    시작이 -1 이 아니고 오늘이 그 앞이면(Date.IsBefore) 거짓
    끝이 -1 이 아니고 오늘이 그 뒤면(Date.IsAfter) 거짓
    인물>0 그리고 친밀도>=0 인데 LAbility::At(인물)->GetFeeling() < 친밀도 면 거짓
    선행이벤트>=0 인데 아직 안 읽었으면 거짓
    번호를 이미 읽었으면 거짓

```

## 5. 달력 [확인]

- 시작 `呼出／オープニング` 이 `L_Calendar::SetDate(4, 8, 0)` 뒤 `SetDate(4, 9, 1)`. `C_GameDate` 의 기본 생성자도 4/9 주=1.
- 끝 `呼出／エンディング実行` 이 `SetDate(11, 17, 6)`.
- `C_GameDate@NextDay`: `주 = (주 + 1) % 7`, `일 > GetMaxDay()` 면 달 넘김.
- `GetMaxDay`: 2월 28, 4·6·9·11월 30, 나머지 31.
- 4/9(주 1)부터 11/17까지 **223일**. EX `日付テスト実行データ` 의 행 수도 **223**이고, 223일째의 주는 `(1+222) % 7 = 6` 으로 `SetDate(11,17,6)` 과 맞는다 — 서로 다른 두 곳이 같은 값을 준다.
- 요일 분기(`呼出／１日の始まり`): 0 일요일 · 1 월요일 · 2~5 화~금 · 6 토요일.
- 특별한 날(요일 분기 대신 전용 경로): **5/15**, **7/23**, **10/21**. 11/11 도 전용 갈래.

## 6. 친밀도 [확인 + 한 군데 가설]

- 값은 `C_Ability` 의 `m_nFeeling`(내부값). 화면값 `GetFeeling()` = 내부값 ÷ `GetFeelingRate()`.
- 비율: 인물 2·3·8 → 420, 4 → 370, 5 → 290, 6 → 540, 7 → 500, 그 밖 420.
- 내부값이 느는 자리는 셋뿐이다(`AddFeeling` 호출자 4곳 중 `■親密度下降` 제외):
  1. `■親密度上昇(인물, 값)` = `AddFeeling(값 × 300)` — 이벤트 25개에서 25회.
  2. `C_SceneTraining@Run` 끝, 고른 상대에게 `AddFeeling(250)`.

## 10. 차트·이동에 쓸 결론

1. 이동은 두 줄이면 된다: `LSys3xScript::PrepareSys("ＥＶ／元／Exxxxx"); LSys3xScript::RunEvent();`
   원작 실행기가 하는 것과 **글자 그대로 같다**. 새 규칙을 넣지 않는다.
2. 릴리스에서는 사슬(`g_EvResult`)을 끌 수 없다 → 한 장면을 부르면 그 뒤로 이어지는 장면까지 돈다. 차트의 「방문 순서」는 이 사슬을 한 덩어리로 세어야 한다.
3. 읽음 표시는 `_EV_TABLE`(이번 판) 을 기준으로 삼는 게 맞다. `GetTotal` 은 회상 76칸 전용이다.
4. 진행 내보내기에 담을 값 — `_EV_TABLE` 전체, `g_sysFlagList` 101칸, `Flags.Date`(월·일·주·남은시간), 인물 2~8 의 `GetFeeling()` 과 `IsTurning()`.

## 11. 던전 묶음의 단계 차례 [확인] — 차트 묶음층 근거

본편 이벤트를 「한 밤의 던전」 한 묶음으로 접을 때, 펼친 단계의 **차례**를 어디서 읽었는지 적는다.

- 한 던전을 맡는 것은 클래스 `C_EventDungeon<맵번호4자리>` 하나다. 그 클래스의 메서드가
  `S_PUSH "Exxxxx"` + `LSys3xScript::Prepare|PrepareSys` 또는 `L_EventCall::CallOnce|CallAlways` 로 이벤트를 부른다.
- 차례는 **(메서드의 함수 번호, 그 메서드 jam 안의 줄 번호)** 로 정했다. AIN 의 함수 번호는 원작이 정의한 차례이고,
  줄 번호는 그 메서드 안에서 실제로 부르는 차례다. 같은 이벤트가 두 번 불리면 **처음 것만** 남긴다.
- 최종장은 클래스가 아니라 `L_DungeonManager::RunEventDungeonEnding{NewTown,School,CenterBuilding}`
  세 함수가 직접 부른다. 이 셋도 같은 규칙으로 「한 밤의 던전」으로 본다.

클래스별 메서드 차례(실측):
